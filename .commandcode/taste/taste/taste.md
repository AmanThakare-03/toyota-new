# Taste
- Strongly prefers surgical, minimal changes to working/approved code: change ONLY the aspect requested and leave layout, structure, content, text, routing, functionality, forms, and API/backend logic untouched. Confidence: 0.85
- Explicitly forbids scope creep on existing projects — no redesigns, rebuilds, new features, extra animations, or unnecessary refactors unless directly asked; when the task is explicitly non-visual, explicitly forbids touching theme, colors, typography, spacing, layout, animations, hover effects or component styling. Confidence: 0.9
- When asked to modify a specific layer (e.g. colors/theme), expects that layer changed globally and consistently while everything else stays byte-for-byte identical. Confidence: 0.8
- Prefers centralized theming — a single source of truth (CSS variables / theme tokens) over scattered hard-coded values — for consistency across an app. Confidence: 0.8
- Expects the agent to first inspect the project's styling architecture (CSS vars, Tailwind, SCSS, CSS modules, etc.) and update the central system first before touching component-level styles. Confidence: 0.78
- Prefers using existing neutral/light-gray colors for cards, sections, borders, and dividers rather than forcing brand colors everywhere; brand colors should be applied intelligently, not blanket find-and-replace. Confidence: 0.7
- Requires sufficient contrast (WCAG-style) for text on backgrounds; won't accept light brand colors for important text on white, and expects interactive elements to stay clearly visible. Confidence: 0.8
- Expects verification before declaring done: run the production build and lint (fix errors introduced, avoid touching unrelated pre-existing warnings), run the app, check major pages, verify responsive behavior across desktop/laptop/tablet/mobile, ensure no new console errors, and exercise real user flows in a browser (deep-links, page refresh, back/forward, internal navigation, search) rather than trusting build success. Confidence: 0.85
- Expects a concise completion report listing: files modified, key changes (e.g. palette used), and build/test results — plus explicit per-item PASS/FAIL/WARNING status for each audited area, an overall deployment-ready verdict, and delivery in the exact section/table structure the request specifies; anything not actually verified must be flagged as such, never claimed as passing. Confidence: 0.85
- Preserves the existing visual hierarchy and design intent when making scoped changes (e.g. mapping old roles to equivalent new roles rather than inventing new ones). Confidence: 0.72
- Insists on truthfulness in content and SEO: never fabricate data — no fake ratings, reviews, prices, offers, PDFs, or unsupported product claims. If something is missing or ambiguous, report it instead of guessing. Confidence: 0.85
- Wants deliverables that ship as a plain static production build (e.g. Vite -> dist/) uploaded to ordinary shared hosting/cPanel: no backend, no Node/PM2/Express runtime on the server, no framework migration (e.g. to Next.js), and no DNS/SSL/hosting changes. Confidence: 0.8
- Performs the live deploy himself — the agent should prepare and verify locally only, never push to or modify production. Confidence: 0.72
- Treats live sites, source projects and backups as READ-ONLY: never modify the original/backup, and make a separate safety backup before starting any edits. Confidence: 0.8
- On migrations, prioritizes SEO and URL continuity: keep existing URLs working, 301 old URLs to new routes only when the new page actually exists, never leave legacy pages 404ing, don't delete legacy pages/assets, and don't remove existing intentional redirects until verified obsolete. Confidence: 0.85
- Prefers the minimum-work compatibility solution (keep serving existing legacy HTML/PDF/image directories, repoint links to real files) over re-implementing existing content in the new stack. Confidence: 0.78
- Prefers autonomous investigation over questions: information discoverable by inspecting the repo/backup must be found, not asked; only genuinely ambiguous items (e.g. conflicting addresses) are surfaced at the end. Confidence: 0.8
- Expects clean, reproducible dependency installs — distrust an existing node_modules, do a fresh `npm ci` — and does not want package-lock.json modified without cause. Confidence: 0.75
- SEO hygiene: no obsolete tags (meta keywords), no fake structured data / aggregate ratings / reviews, no duplicated meta tags; prefer locally hosted assets over fragile external URLs (e.g. og:image). Confidence: 0.8
- One logical page = one URL: the same page must use an identical canonical path from every location (header, dropdowns, mobile menu, footer, cards, CTAs, breadcrumbs, related content, search index, sitemap, canonical metadata). Alternate/old paths may survive only as redirects and must never appear as a live link target; no duplicate components/routes serving one page. Confidence: 0.85
- Prefers a single centralized source of truth for route/URL definitions (e.g. a routes config) that navigation, the router, SEO config and the sitemap all derive from, so link targets can't drift — reuse/extend the existing architecture rather than adding a second parallel config. Confidence: 0.8
- Treats the live production site as the authoritative reference for its own URLs: preserve its exact spellings (including apparent typos) and verify against the live site before "correcting" anything; don't silently normalize. Confidence: 0.78
- Expects an exhaustive repo-wide audit before changes — every file type and every referencing surface, including secondary/hidden places (config, constants, JSON, markdown, comments/commented-out code, generated files, sitemap, server config, tests) — not just the obvious component. Confidence: 0.78
- Writes long, exhaustively numbered specs and expects each numbered requirement addressed and evidenced individually (e.g. a per-item report matching the requested sections) rather than a general summary. Confidence: 0.72
